## 1. Project Overview

The Online Transaction Fraud Detection System is a machine learning application developed to identify potentially fraudulent financial transactions. It uses transaction details such as transaction amount, transaction type, sender balance, and receiver balance to estimate the likelihood of fraud.

The system provides a Streamlit dashboard with manual transaction checking, simulated real-time monitoring, fraud-risk visualization, and Local Interpretable Model-Agnostic Explanations (LIME).

## 2. Problem Statement

Financial transaction datasets contain a large number of genuine transactions and a much smaller number of fraudulent transactions. This class imbalance makes fraud detection challenging. A model can show high overall accuracy while failing to detect fraud cases.

This project explores machine learning techniques for identifying fraud, handling class imbalance, comparing model performance, and explaining individual predictions.

## 3. Objectives

- Develop a machine learning model for transaction fraud detection.
- Preprocess transaction data and encode categorical transaction types.
- Address class imbalance using Synthetic Minority Over-sampling Technique (SMOTE).
- Compare Logistic Regression, Random Forest, Decision Tree, and XGBoost.
- Evaluate models using precision, recall, F1-score, ROC-AUC, and confusion matrices.
- Develop an interactive Streamlit application.
- Use LIME to explain individual model predictions.

## 4. Dataset

The project notebook uses the PaySim synthetic financial transaction dataset.

The notebook contains 6,362,620 transaction records and uses the following input features:

- Step
- Transaction amount
- Original sender balance
- New sender balance
- Original receiver balance
- New receiver balance
- CASH_OUT transaction indicator
- DEBIT transaction indicator
- PAYMENT transaction indicator
- TRANSFER transaction indicator

The target variable is `isFraud`, where 0 represents a genuine transaction and 1 represents a fraudulent transaction.

The notebook removes `nameOrig`, `nameDest`, and `isFlaggedFraud` from the model input features.

## 5. Data Preprocessing

The notebook performs the following preprocessing steps:

1. Removes selected identifier and flag columns.
2. Converts the transaction type into binary indicator features.
3. Separates the input features and target label.
4. Splits the dataset into training and testing sets using stratified sampling, with 80% for training and 20% for testing.
5. Applies SMOTE to the training data to balance the classes.
6. Standardizes the input features using `StandardScaler`.

SMOTE is applied to training data rather than the held-out test data.

## 6. Model Development and Selection

The notebook compares four machine learning models:

- Logistic Regression
- Random Forest
- Decision Tree
- XGBoost

Model performance is evaluated using accuracy, precision, recall, F1-score, ROC-AUC, and confusion matrices. The notebook prioritizes fraud recall and F1-score when calculating its model ranking score:

`Rank Score = 0.7 × Recall + 0.3 × F1-score`

In the original model comparison, the Decision Tree achieved a recall of approximately 96.10%, precision of 70.93%, F1-score of 81.62%, and ROC-AUC of 98.03%.

These figures describe the original Decision Tree experiment and must not be presented as results of the isotonic-calibrated model.

## 7. Application Development

The application is developed using Streamlit and provides two modes.

### 7.1 Real-Time Monitoring

This mode generates simulated transactions and displays their predicted fraud probabilities, risk classifications, recent transaction records, summary metrics, and probability trends.

The transactions generated by this demonstration are synthetic scenarios. Their scenario names do not establish ground-truth fraud labels.

### 7.2 Manual Transaction Check

Users enter the transaction step, amount, sender balances, receiver balances, and transaction type. The application passes these features to the saved model and displays the resulting fraud probability and risk classification.

### 7.3 Risk Explanation

The application displays rule-based risk indicators, such as unusually large amounts, sender-balance mismatches, and selected transaction types. These indicators are separate from the model's learned prediction.

## 8. Explainable Artificial Intelligence Using LIME

The application uses LIME to provide a local explanation of an individual prediction. It perturbs the input features and approximates the model's behavior around the selected transaction.

The application displays feature contributions in a table and chart to help users understand which features influenced the local explanation.

LIME provides an approximate explanation, not proof that a transaction is fraudulent.

## 9. Model Calibration and Evaluation

The notebook includes an experiment with an isotonic-calibrated Decision Tree. In the current recorded evaluation, this version produced only two distinct probability values and achieved zero fraud recall at a classification threshold of 0.5.

This result indicates that the isotonic experiment requires further investigation before it can be claimed to improve fraud detection or probability calibration.

The original Decision Tree and the calibrated model should be evaluated separately using the same untouched test set. Model performance should be reported for the exact model used in the final application.

## 12. Limitations

- PaySim is a synthetic dataset and may not represent every pattern found in real financial transactions.
- High accuracy alone is not sufficient to establish successful fraud detection.
- Simulated transactions in the dashboard do not have verified labels.
- The isotonic-calibrated model's current evaluation does not demonstrate successful fraud detection at the 0.5 threshold.
- LIME explanations are local approximations and should not be treated as causal evidence.

## 13. Future Enhancements

- Further investigate calibration and probability reliability.
- Evaluate the final model on a held-out dataset and report fraud-specific metrics.
- Add testing using real labelled test-set examples.
- Improve monitoring, logging, and user feedback.
- Explore deployment and integration with transaction-processing systems.

## 14. Conclusion

This project demonstrates a machine learning workflow for financial transaction fraud detection, including data preprocessing, class balancing, model comparison, model evaluation, an interactive Streamlit dashboard, and local explanations using LIME.

The project highlights the importance of evaluating fraud recall and precision rather than relying only on overall accuracy. Calibration and model selection must also be verified before deploying the final version.
